# ILA Probe Map — A7-Drift / Boot-Wedge Bisection

> **Purpose.** Live cycle-accurate capture of CPU + dcache + AXI state
> during the post-DAFB Q700 boot wedge (`exc_pc=0x4086abb2`,
> `exc_count=0x12c5`, `pc_live=0x6db6db6d`).  Four CPU-side principled
> fixes have all passed sim but left HW behaviour bit-identical — the
> remaining bug class is either a CPU pipeline gate-level race OR a
> dcache/DRAM writeback race.  This ILA gives us the smoking-gun
> waveform.

> **2026-07-04 update — bit-rot fix + v6 probes.** The whole probe map
> below went dead when the CPU was carved into the separate `m68k-ooo`
> repo and wired back in as a git submodule behind `rtl/soc/cpu_socket.vh`
> (2026-05-27 split): `make impl ENABLE_ILA=1` failed elaboration because
> `rtl/soc/fpga_top_debug_vio.vh` referenced `dbg_ila_*_w` wires that the
> CPU submodule computed internally (`m68k_axi_wrapper.v`) but never
> exposed as module ports.  Fixed by promoting them all to real
> `ifdef ILA_ENABLE`-gated output ports (see `rtl/soc/cpu_socket.vh`
> group 7, `rtl/core/m68k_axi_wrapper.v` in the CPU repo, and
> `rtl/soc/fpga_top_debug_ctrl.vh`'s `u_cpu` instantiation).  Probes
> 32-34 are new: `exc_held_a7_phys`, `take_rte_finalize`, and
> `supervisor_mode` — added for the live A7/RTE-finalize investigation
> (bracket a real `take_rte_finalize` event on hardware; see the CPU
> repo's `docs/tracks/core.md` bisect notes for the A7-corruption-at-RTS
> lead this feeds).  See `synth/debug_ila.tcl`'s top-of-file comment for
> the authoritative v6 probe list and bit-width accounting.

The IP is generated by `synth/debug_ila.tcl` (sourced from
`synth/vivado.tcl`) and instantiated under `\`ifdef ILA_ENABLE` in
`rtl/fpga_top_debug_vio.vh` (instance name `u_dbg_ila`).  Same
IP-flow as `debug_vio` — no `create_debug_core` / `mark_debug`
auto-insertion (Vivado 2025.2 has a known issue with that path; see
the long comment at `synth/vivado.tcl:40-50`).

## Enabling

```bash
ENABLE_ILA=1 make synth          # synth_only with ILA core
ENABLE_ILA=1 make impl           # full impl (bake)
```

The flag defaults OFF — the ILA costs roughly 28-32 BRAM-18Kb tiles
+ a few thousand LUTs and is only useful while bisecting the wedge.

## v4 probe map additions (2026-05-27) — snap-mux bypass + IF/BPU PC tap

**Why these probes exist.**  `probe10` (`arch_a7_val`) is read through
`arch_a7_or_snap_addr` in `m68k_core_execute.vh`: when `effective_halt`
asserts (e.g. the cycle pcmis fires and the CPU auto-halts on a wild
PC), the PRF read address flips from `committed_a7_phys` to
`snap_prf_idx_i`.  The probe then reports whatever PRF slot the JTAG
snap chain happens to be pointing at — not the true A7.  The
`0xFFFFFFF6` "corruption" observed in prior captures is very likely an
artifact of this mux, not real PRF drift.  v4 adds raw, mux-bypassed
taps so we can prove or disprove the artifact in a single capture.

| # | Width | Signal                       | Source                                                                |
|---|-------|------------------------------|-----------------------------------------------------------------------|
| 25| 32    | `prf[committed_a7_phys]`     | RAW PRF read of the committed A7 phys — no mux gating.  This is the TRUE live A7 value regardless of halt state. |
| 26| 32    | `prf[7'd1]`                  | RAW PRF read of phys 0x01 — sanity tap (committed_a7_phys is observed = 0x01 at the wedge). |
| 27| 7     | `snap_prf_idx[6:0]`          | JTAG snap chain's current PRF index — i.e. the address probe10 mirrors when halted. |
| 28| 1     | `effective_halt`             | When 1, probe10 starts lying.  Trigger on this rising edge to capture the exact halt cycle. |
| 29| 32    | `if_pc[31:0]`                | IF-stage live fetch PC.  Captures the wrong-PC fetch (0x6db6db6d) the cycle before pcmis. |
| 30| 32    | `pred_target_sel[31:0]`      | BPU/RAS predicted next-PC.  Shows if the BPU mispredicted to the wild target. |

### Trigger recipe (v4)

```tcl
# After open_hw_target / refresh_hw_device:
set probe28 [get_hw_probes u_dbg_ila/probe28 -of_objects [get_hw_ilas hw_ila_1]]
# probe28 = effective_halt (1b).  Trigger on the rising edge of the halt.
set_property TRIGGER_COMPARE_VALUE eq1'b1 $probe28
set_property CONTROL.TRIGGER_POSITION 3500 [get_hw_ilas hw_ila_1]
set_property CONTROL.DATA_DEPTH 4096        [get_hw_ilas hw_ila_1]
run_hw_ila [get_hw_ilas hw_ila_1]
wait_on_hw_ila [get_hw_ilas hw_ila_1]
display_hw_ila_data [upload_hw_ila_data hw_ila_1]
```

Then in the displayed table:
- Compare `probe10` (arch_a7_val) vs `probe25` (prf[committed_a7_phys])
  cycle-by-cycle.  If they differ ONLY on cycles where `probe28=1`,
  the prior "A7 corruption" was the snap-mux artifact, not real drift.
- Look at `probe29` (if_pc) the cycle before `probe28` rises — that is
  the wrong PC the CPU was about to execute.
- Look at `probe30` (pred_target_sel) the cycle before that — that is
  the BPU's mispredict that set up the wild fetch.

`dc_aw_is_evict` is a new output added to `dcache.v` that distinguishes
writebacks (per-line victim, full-cache flush walker, or CPUSH LINE)
from bypass / uncached stores by inspecting the dcache FSM `state`.

## v7 probe map additions (2026-07-04) — rte_acc[0] capture-race hunt (task #89)

The v6 capture (see the coordinator's live-HW findings, 2026-07-04)
confirmed the mechanism precisely: at a real `take_rte_finalize` event
(exc_count=0x12d1, ROM PC 0x40809b88 — the RTE ending the autovector
level-1 IRQ dispatcher glue), `a7_writeback_val` (probe23) read back as
exactly `0x00000000` and `supervisor_mode` (probe34) dropped 1→0 in the
same cycle, while `committed_a7_phys` (probe2) and `exc_held_a7_phys`
(probe32) stayed pinned to the SAME phys reg (0x1a) throughout — this
DEFINITIVELY RULES OUT a RAT-rename / phys-register-reuse hazard.
`commit.v`'s RTE-finalize block derives `saved_sr_w` from the persistent
`rte_acc[0]` register (`rte_acc[0][31:16]`); reading `saved_sr_w[13]==0`
(user-mode) caused the mode-restore logic to pick `prf_usp_val` (an
uninitialized/stale USP) instead of staying supervisor.  `rte_acc[0]` is
written at the FIRST RTE-pop LOAD's own earlier retire
(`rte_acc[rob_rte_word_idx] <= rob_br_target`, gated on `rob_is_rte_pop`).
These probes bisect why that write is missing/wrong by watching the
register itself plus the ROB completion path (`cmpl1` = LSU completion
bus) that must fire before that LOAD can retire — specifically whether
`rob.v`'s tag-wraparound staleness guard (`cmpl1_stale = cmpl1_alloc_epoch
!= alloc_epoch[cmpl1_tag]`) ever drops that completion.

| # | Width | Signal                       | Source                                                                |
|---|-------|------------------------------|-------------------------------------------------------------------------|
| 35| 32    | `rte_acc0[31:0]`             | commit.v — persistent `rte_acc[0]` register, raw.                       |
| 36| 1     | `rob_is_rte_pop`             | ROB head is an RTE-pop LOAD retiring this cycle.                        |
| 37| 3     | `rob_rte_word_idx[2:0]`      | Which `rte_acc[]` slot this retire targets (0 = SR+PC-hi word).         |
| 38| 32    | `rob_br_target[31:0]`        | ROB-head data field at this retire — what SHOULD land in rte_acc[idx].  |
| 39| 1     | `cmpl1_en`                   | LSU completion bus (rob.v's cmpl1) firing this cycle.                   |
| 40| 6     | `cmpl1_tag[5:0]`             | ROB tag this cmpl1 completion targets.                                  |
| 41| 1     | `cmpl1_alloc_epoch`          | Epoch carried by this completion (compare against the tag's live epoch).|
| 42| 1     | `cmpl1_stale`                | 1 = rob.v's staleness guard dropped this completion (no e_complete/e_br_target write). |
| 43| 6     | `rob_head_idx[5:0]`          | Live ROB head index — at a retire cycle this IS the retiring entry's own tag. |

### Trigger recipe (v7)

```tcl
# After open_hw_target / refresh_hw_device:
set ila [get_hw_ilas hw_ila_1]
set p36 [get_hw_probes u_dbg_ila/probe36 -of_objects $ila]   ;# rob_is_rte_pop
set p37 [get_hw_probes u_dbg_ila/probe37 -of_objects $ila]   ;# rob_rte_word_idx
# Trigger on the FIRST RTE-pop LOAD retiring (word idx 0) — this is the
# retire that is SUPPOSED to write rte_acc[0].
set_property TRIGGER_COMPARE_VALUE eq1'b1  $p36
set_property TRIGGER_COMPARE_VALUE eq3'd0  $p37
set_property CONTROL.TRIGGER_POSITION 2048 $ila
run_hw_ila $ila
wait_on_hw_ila -timeout 1 $ila     ;# NOTE: -timeout is in MINUTES, not seconds
display_hw_ila_data [upload_hw_ila_data $ila]
```

In the displayed table:
- Confirm `probe38` (rob_br_target) at the trigger sample holds a
  plausible SR+PC-hi word (not zero) — this is the data the retire
  is ABOUT to commit.
- Check `probe35` (rte_acc0) on the FOLLOWING sample — does it now
  equal probe38's value?  If yes, the write landed correctly and the
  corruption must be introduced later (re-examine the second
  RTE-pop-load / finalize path, or a subsequent stray write to the
  same register — not currently probed, would need a v8 tap on
  `rte_acc[1]` / the finalize block's own read timing).
- If `probe35` does NOT pick up probe38's value, scan backward from the
  trigger for the completion that made THIS retire possible: look for
  `probe39`(cmpl1_en)==1 && `probe40`(cmpl1_tag) == `probe43`(rob_head_idx
  at the trigger sample) — i.e. the earlier cycle where this exact ROB
  tag's LSU completion fired.  If `probe42`(cmpl1_stale)==1 on THAT
  completion, rob.v silently dropped it (no `e_complete`/`e_br_target`
  write) — meaning the entry that just retired became "complete" via
  some OTHER, later completion event on a recycled tag, and
  `rob_br_target` at retire time is whatever THAT unrelated completion
  wrote (very plausibly stale/zero) rather than the genuine popped SR.
  That would confirm the ROB completion-tag-wraparound/aliasing theory
  as the true root cause.

## v7b/v7c/v7d probe map additions (2026-07-04) — MOVE-to-SR bisected to the exact corruption cycle (task #89)

**Live break_pc bisection (coordinator) found the exact corrupting
instruction**: `move (sp)+,sr` at ROM PC `0x408701AE` — a hand-rolled
epilogue, NOT an RTE. Before it, A7/SR are sane; immediately after,
both read `0x00000000`, with exactly one nested F-line exception (vec
`0x0b`) taken at an unrelated PC inside that one instruction's window.

**RTL-confirmed why the eventual bus-error's `fault_addr == PC`**:
the CPU repo's `rtl/core/m68k_core_memory.vh:106-111` wires the
fetch-side MMU's `.supervisor(arch_sr_s_w)` directly to commit.v's live
`arch_sr[13]`. `mmu.v:299`'s `atc_hit_sup_fault = atc_hit &
atc_hit_sup_only & ~supervisor` is a real, wired permission check. Once
`arch_sr` is corrupted to 0, the next instruction fetch is legitimately
evaluated as user-mode against supervisor-only ROM space and fails —
this is a correct downstream consequence, not a second bug.

**v7b (probes 44-46)** — `commit.v`'s `SYS_MOVE_SR` retire shares the
same `a7_writeback_en/phys/val` staging registers as RTE-finalize, but
gates on `sys_move_word_val` — a LIVE combinational PRF read
(`rob_src_a_val = prf[rob_phys_src_a]`), not a latched accumulator like
`rte_acc[0]`.

| # | Width | Signal                | Source                                                    |
|---|-------|------------------------|------------------------------------------------------------|
| 44| 6     | `rob_uop_op[5:0]`      | Retiring µop's opcode (SYS_MOVE_SR = 12)                    |
| 45| 1     | `rob_has_src_a`        | Retiring µop has a valid src_a operand                       |
| 46| 32    | `rob_src_a_val[31:0]`  | src_a value (= sys_move_word_val's source)                   |

**v7c (probes 47-50)** — LSU issue-time base value for the RTS's own
stack-pop LOAD (a separate, now largely-explained anomaly — see above).

**v7d (probe 51)** — the smoking-gun follow-up tap:

| # | Width | Signal                     | Source                                          |
|---|-------|-----------------------------|--------------------------------------------------|
| 51| 7     | `rob_phys_src_a[6:0]`       | The phys-reg TAG (not value) this µop reads for src_a |

### Live capture result (deterministic, PC-based trigger — fires in ~4s)

```tcl
set p44 [get_hw_probes ila_rob_uop_op   -of_objects $ila]  ;# SYS_MOVE_SR == 6'h0c
set p13 [get_hw_probes dbg_ila_rob_pc_w -of_objects $ila]  ;# fixed ROM PC of the bug
set_property TRIGGER_COMPARE_VALUE eq6'h0c     $p44
set_property TRIGGER_COMPARE_VALUE eq32'h408701ae $p13
set_property CONTROL.TRIGGER_CONDITION AND $ila
```

Captured (`synth/ila_move_sr_capture.tcl`): `rob_src_a_val` reads a
stable, valid `0x001fdb62` for 8+ cycles while this µop stalls at/near
the ROB head, then reads **exactly `0x00000000`** at the retire cycle
(sample 2048 in the capture), immediately followed (sample 2049) by
`a7_writeback_en=1, a7_writeback_phys=0x01, a7_writeback_val=0`, and
`supervisor_mode` dropping 1→0 — commit.v's own logic faithfully
propagating the corrupted read. A CDB0 write to phys reg `0x01`
(value `0x001fdb64`) lands 4 cycles before the retire (sample 2044),
coincident with `committed_a7_phys` transitioning to `0x01` (sample
2046) — suggestive of, but not yet proven to be, the nested F-line
exception's own A7-rename activity colliding with this stalled µop's
operand slot. **v7d's `rob_phys_src_a` tap exists to close this last
gap**: does the phys tag itself change (RAT/rename bug), or does it
stay constant while the slot's value changes underneath it (stale
completion write, same class as the `cmpl1_stale`/`alloc_epoch` fix in
`279d7cb4`)?

## Trigger Recipes

Vivado HW Manager / `hw_ila` Tcl trigger setup, run **after**
`open_hw_target` and `current_hw_device`:

### 1.  A7 jumps by an illegitimate step

Catches USP/SSP/ISP drift like the post-DAFB `-8` wedge.  The RTL
computes `ila_a7_illegitimate_step` combinationally — its
"legitimate" set is `{0, ±4, ±8, ±12, ±16, ±32}`, and this bit goes
high any time `arch_a7_val` changes by something outside that set.
It is wired as **bit [4] of probe5** so the Vivado HW Manager can
trigger on it directly:

```tcl
# After open_hw_target / refresh_hw_device:
set probe5 [get_hw_probes u_dbg_ila/probe5 -of_objects [get_hw_ilas hw_ila_1]]
# probe5 = {a7_illegitimate_step, rob_pop, rob_is_last_uop, mb_empty, drain_active}
# Trigger when bit[4]=1 (mask the lower 4 bits with X).
set_property TRIGGER_COMPARE_VALUE eq5'b1xxxx $probe5
set_property CONTROL.TRIGGER_POSITION 2048 [get_hw_ilas hw_ila_1]
set_property CONTROL.DATA_DEPTH 4096      [get_hw_ilas hw_ila_1]
run_hw_ila [get_hw_ilas hw_ila_1]
wait_on_hw_ila [get_hw_ilas hw_ila_1]
display_hw_ila_data [upload_hw_ila_data hw_ila_1]
```

### 2.  Any exception/trace fire

```tcl
set_property TRIGGER_COMPARE_VALUE neq8'h00 \
    [get_hw_probes u_dbg_ila/probe9 -of_objects [get_hw_ilas hw_ila_1]]
set_property CONTROL.TRIGGER_POSITION 2048 [get_hw_ilas hw_ila_1]
run_hw_ila [get_hw_ilas hw_ila_1]
```

### 3.  Writeback to a specific physical address

For example, "trigger when the dcache evicts a line within the
suspect range `0x0000_0000..0x0000_FFFF`":

```tcl
set probe14 [get_hw_probes u_dbg_ila/probe14 -of_objects [get_hw_ilas hw_ila_1]]
# probe14 = {raw_daxi_awaddr[31:0], wb_valid}
# Trigger when wb_valid=1 AND addr matches mask
set_property TRIGGER_COMPARE_VALUE eq33'h0000_xxxx_1 $probe14
set_property CONTROL.TRIGGER_POSITION 2048 [get_hw_ilas hw_ila_1]
run_hw_ila [get_hw_ilas hw_ila_1]
```

### 4.  flush_en pulse (pipeline squash)

Quick way to see what microarchitectural events bracket a flush:

```tcl
set_property TRIGGER_COMPARE_VALUE eq1'b1 \
    [get_hw_probes u_dbg_ila/probe4 -of_objects [get_hw_ilas hw_ila_1]]
set_property CONTROL.TRIGGER_POSITION 2048 [get_hw_ilas hw_ila_1]
run_hw_ila [get_hw_ilas hw_ila_1]
```

### 5.  Advanced — wedge PC

When the wedge is reproducibly at `0x4086abb2`:

```tcl
set_property TRIGGER_COMPARE_VALUE eq32'h4086abb2 \
    [get_hw_probes u_dbg_ila/probe13 -of_objects [get_hw_ilas hw_ila_1]]
set_property CONTROL.TRIGGER_POSITION 3500 [get_hw_ilas hw_ila_1]  ;# mostly pre-trigger
run_hw_ila [get_hw_ilas hw_ila_1]
```

## Implementation Notes

- **Clock.** The ILA samples on `core_clk` (same as the VIO),
  100 MHz nominal.  At 100 MHz the 4096-sample capture window is
  40.96 µs of execution.  Adjust `C_DATA_DEPTH` in
  `synth/debug_ila.tcl` if longer history is needed (doubles BRAM
  usage per step).
- **Input pipeline.** `C_INPUT_PIPE_STAGES=1` adds one register
  stage on the probe inputs so the ILA's data-net fanout into the
  capture BRAMs doesn't add to the critical path of the CPU.
- **Capture storage qualification.** `C_EN_STRG_QUAL=1` is on so a
  HW Manager user can also restrict captures to a window of
  interest (e.g. only sample while `effective_halt=0`), keeping
  the 4 K-sample window denser around real activity.
- **No TRIGOUT/TRIGIN.** This ILA is standalone — no daisy-chained
  ILA-to-ILA cross-trigger.  If we ever want to gate this against
  the VIO probe_out0 dashboard bit, add `C_TRIGIN_EN=true` and
  wire a top-level VIO output bit into a new ILA TRIG_IN port.
- **MARK_DEBUG.** All probe-source wires (declared in
  `rtl/fpga_top_cpu.vh`) carry `(* MARK_DEBUG = "true" *)` so
  opt_design / place_design preserve the signal identity needed
  for the ILA hub.  `setup_debug_ila` in `synth/vivado.tcl`
  re-applies the property post-synth as a belt-and-suspenders.
- **Real-MIG builds** intentionally skip the MARK_DEBUG re-apply
  on the DDR-adjacent probe nets (same constraint as the VIO).
  The probe nets themselves remain MARK_DEBUG'd via the inline
  attribute.

## Output Files

- `build/<impl>/checkpoints/synth.dcp` — synth checkpoint with ILA
  inferred.  Look for `inst .* debug_ila` in the synth log for the
  inferred instance count.
- `build/<impl>/fpga_top.ltx` — debug probes file, loaded
  automatically when the bitstream is programmed.
- `build/<impl>/reports/utilization_synth.rpt` — BRAM count should
  increase by ~28-32 vs the non-ILA build.

## Capture Workflow

```bash
# Program the FPGA (or boot from flash) with an ENABLE_ILA=1 bitstream.
# Open one Vivado session and one JTAG REPL session:
mkfifo /tmp/jtag_in
nohup bash -c 'exec 7>/tmp/jtag_in; sleep 99999' >/dev/null 2>&1 & disown
nohup bash -c "vivado -mode tcl -nojournal -nolog \
  -source tools/jtag_repl.tcl -tclargs build/.../fpga_top.bit \
  build/.../fpga_top.ltx < /tmp/jtag_in > /tmp/jtag_out 2>&1" &

# Inside Vivado:
open_hw_target
current_hw_device [lindex [get_hw_devices] 0]
refresh_hw_device [current_hw_device] -update_hw_probes false
# Set up trigger (see recipes above) and run.
```

The ILA only captures while the CPU is running (the probes are on
`core_clk`); if the CPU is held in reset via `vio_boot_ctrl[3]`,
no useful data lands in the capture buffer.

## Adding Probes Later

To grow the probe count past 16 or widen an existing probe:

1. Edit `synth/debug_ila.tcl` — update `C_NUM_OF_PROBES` and the
   `CONFIG.C_PROBEn_WIDTH` list.
2. Bump the marker version (`ila_probe_map=v2`) so the IP-cache
   regenerates instead of reusing the stale OOC DCP.
3. Wire the new RTL bundle through `m68k_core.v` (output port),
   `fpga_top_cpu.vh` (top-level wire + connection), and
   `fpga_top_debug_vio.vh` (`u_dbg_ila` probe N).
4. Update this doc.

Keep probes ≤ ~256 bits total / 32 BRAMs unless you also size up the
`bench_baseline.md` BRAM budget for the build.
